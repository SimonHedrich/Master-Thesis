## Protocol

- Batch size 1; core affinity pinned with `taskset`; thread count passed explicitly to each runtime; `performance` governor.
- 3 independent process invocations per cell; the headline is the median of the pooled runs, and the spread across invocations is reported so process-level variance stays visible.
- Iteration counts adapt to a per-window wall-clock budget (nominal 20 warm-up / 100 measured); the realised `n` is in `latency_summary.csv`.
- Deployment regime: conf 0.25, IoU 0.45, max_det 100.
- `W_infer` is the MLPerf-Tiny-scoped window (forward call only). `W_e2e` adds decode, letterbox and post-processing — it is the number that answers the per-frame budget question.

## Verdict against the design targets

Targets are **project design estimates, not vendor-certified figures**: ≤30 ms per frame at 640×640 and ≤500 MB, from `docs/2026-03-10_object-detection-models-for-embedded-systems.md` §1.

`docs/2026-03-09_hardware-proxy-selection.md` rates the Pi 4/400 at −10 % CPU versus the QCS605, so QCS605 ≈ Pi 400 × 0.85–0.90, i.e. a Pi 400 measurement of **≤33–35 ms** would imply ≤30 ms on the QCS605 CPU. **This applies to the CPU path only** — the Pi 400 has no analogue to the Hexagon 685 DSP and its VideoCore VI is far weaker than the Adreno 615.

## Non-claims

- **FP32, unoptimized.** No PTQ, QAT or pruning was applied. ONNX Runtime applies its own graph optimizations at session creation (`ORT_ENABLE_ALL`), which is recorded per cell; the shipped ONNX graph is the unmodified export (onnxslim was run for inspection only and is not shipped).
- **A bounded measurement campaign on one device**, not a benchmarking study.
- **No power or thermal-envelope measurement.** The Pi has no instrumented rail, and no power budget for the AX Visio is documented anywhere in this repo.
- **The QCS605's accelerated path is entirely unproxied.** The Hexagon 685 DSP (~2.1 TOPS) has no analogue on this device. The translation rule above covers the CPU path only.
- **No GPU number.** See `ncnn_conversion_finding.md`: the device's Vulkan stack works (V3D 4.2.14.0, Vulkan 1.3.354, Mesa 26.2.2) and the `ncnn` wheel ships with Vulkan compiled in, but `pnnx` crashes converting both detectors, so no NCNN model could be produced.
- Models exported without trained weights are valid for latency only and are excluded from parity; `latency_summary.csv` carries `weights_source` and `parity_valid` per row.
